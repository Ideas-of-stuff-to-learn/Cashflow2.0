## Part 1: Manual review flow optimisation

### Background

After a categorisation run (or on login if leftover items exist), a blocking two-stage overlay forces the user to resolve any `NEEDS_MANUAL_REVIEW` transactions before doing anything else. Stage 1 (`ManualReviewStatsModal`) shows counts and asks "Categorise Now" or "Put in Other". Stage 2 (`ManualReviewSequentialModal`) steps through each transaction one at a time with category buttons.

### Problems fixed

**1a. Sequential picks: N API calls → 1**

The old `handleSequentialPick` in `ManualReviewGate` fired `POST /categorize/resolve` for each transaction the user clicked through. 50 transactions = 50 sequential round trips.

Fix: picks are now accumulated into a `pendingResolutionsRef` (a `useRef` array). Local state updates happen immediately on each click so the UI advances instantly with no waiting. When the user resolves the last transaction, the entire batch is flushed in one `resolveCategories()` call. The backend's `/categorize/resolve` already accepts an array and handles them all in one DB transaction — no backend changes needed.

On flush failure: the modal stays open and shows an error state with a "Retry" button. The pending batch is preserved in the ref, so retrying re-sends the exact same array without the user needing to re-pick anything.

**1b. "Put in Other": per-item loop → single SQL UPDATE**

The old `handlePutInOther` called `resolveCategories()` with the full `needsReviewItems` array — one backend call, but the backend's `/categorize/resolve` loops through each item doing cache lookups, cache writes, and two potential UPDATE statements per item. Slow for large counts.

Fix: `handlePutInOther` now calls a new `resolveRemainingToOther()` function (added to `api.jsx`) which hits `/categorize/resolve-remaining-to-other`. This endpoint already existed in the backend — it does a single `UPDATE transactions SET category = 'Other' WHERE user_id = ? AND category = NEEDS_MANUAL_REVIEW`, one SQL statement regardless of count.

**1c. Page-unload safety net**

If the user closes the tab mid-sequential, any transactions still `NEEDS_MANUAL_REVIEW` in the DB would persist. The backend already had `/categorize/resolve-remaining-to-other` and a comment about `sendBeacon` — it was just never wired up on the frontend.

Fix: a `pagehide` event listener in `ManualReviewGate`, active only when `stage === 'sequential'`, fires `navigator.sendBeacon('/categorize/resolve-remaining-to-other')`. The endpoint takes no body — the JWT httpOnly cookie is sent automatically by the browser with any same-origin request including sendBeacon. Any `NEEDS_MANUAL_REVIEW` items still in the DB get swept to Other.

Note: in-progress picks that haven't been flushed yet (sitting in `pendingResolutionsRef`) are lost on page close. Those items come back as `NEEDS_MANUAL_REVIEW` on next login and the existing overlay catches them.

If the user closes during stage `stats` (hasn't clicked either button yet), no sendBeacon fires — there's nothing to do because no picks have been made. The existing on-login check (`startManualReviewFlowIfNeeded` called after `loadInitialData` completes) re-triggers the flow when they next log in.

### Files changed

- `api.jsx` — added `resolveRemainingToOther()` (async fetch) and `beaconResolveRemainingToOther()` (sendBeacon wrapper)
- `ManualReviewGate.jsx` — full rewrite of pick/flush/error logic; added `pagehide` listener; switched "Put in Other" to use `resolveRemainingToOther()`
- `ManualReviewSequentialModal.jsx` — added `flushing`, `flushError`, `isDone`, `onRetry` props with corresponding UI states (saving spinner, error+retry, all-done)

## Part 2: Chart filter bug — deselect all didn't clear bars

### The bug

In `buildStackData.jsx`, the visibility check for each bar segment was:
```js
const visible = selectedCategories.size === 0 || selectedCategories.has(category);
```

The `size === 0` guard was a legacy "empty means show everything" sentinel from an earlier version of the filter model. AppContext was later refactored to proper checkbox-list semantics where empty genuinely means nothing selected / nothing shown — but `buildStackData` never got updated to match. So deselecting all categories produced an empty Set, the guard fired, and every bar still rendered as if nothing was filtered.

### The fix

Remove `selectedCategories.size === 0 ||`. One character change:
```js
const visible = selectedCategories.has(category);
```

Empty set → nothing visible. Consistent with the checkbox-list model everywhere else.

### File changed

- `App/WebUI/src/utils/charts/buildStackData.jsx` line 44

## Part 3: Transaction list virtualisation

### The problem

`ContentsScreen` rendered every transaction in `filtered` as a DOM node:
```jsx
{filtered.map(item => <TransactionRow ... />)}
```

With thousands of transactions, toggling a filter checkbox caused React to mount or unmount thousands of DOM nodes in one synchronous render, freezing the browser for a noticeable half-second.

### The solution

`@tanstack/react-virtual` (supports React 19 — `react-window` v1 does not). The `.table` div already had `flex: 1; overflow-y: auto` (fixed-height scrollable container) and `TransactionRow` already had a fixed `height: 46px` defined in both CSS and as `ROW_HEIGHT = 46` in `contentsUtils.jsx`. These are exactly the conditions that make virtualisation a clean retrofit.

The virtualiser tracks the scroll position of the `.table` div and renders only the ~20-30 rows currently in view plus a small overscan buffer, inside a single tall container div that gives the scrollbar the correct total height. DOM node count stays constant (~30) regardless of how many transactions exist.

All filtering, sorting, and search logic is unchanged — `filtered` is still computed the same way in `useCategoryFilters`. The virtualiser just renders a window into it. Selection state, row count display, bulk operations — all unaffected.

### Files changed

- `App/WebUI/package.json` — added `@tanstack/react-virtual`
- `ContentsScreen.jsx` — replaced `filtered.map(...)` with `useVirtualizer` from `@tanstack/react-virtual`; added `tableRef` pointing at the `.table` div as the scroll element
- `TransactionRow.jsx` — added `style` prop spread onto the root `<button>` (required by the virtualiser for absolute positioning)

### Note on library choice

`react-window` v2 (what npm installed by default) has a completely different API than v1 and doesn't export `FixedSizeList`. `react-window` v1 has no React 19 peer dep support. `@tanstack/react-virtual` is the correct modern choice — no wrapper component needed, just a hook.

## Part 4: Auto LAN IP detection in dev setup

### The problem

`App/frontendLocalConfig.jsx` and `App/backendLocalConfig.py` both had the LAN IP hardcoded (`192.168.0.101`). When DHCP reassigned the IP, both files had to be manually updated.

### The solution

`start-dev.sh` now detects the LAN IP at launch time and writes `App/.env` (which is gitignored) before starting either server. Both config files read the IP from that env file instead of hardcoding it.

**IP detection logic (Windows):**
```bash
IPCONFIG=$(ipconfig | tr -d '\r')   # strip Windows \r line endings first
WIFI_IP=$(echo "$IPCONFIG" | awk '
    /adapter WiFi|adapter Wi-Fi/ { in_block=1; next }   # next skips reset-pattern on same line
    in_block && /IPv4/ { split($0, a, ": "); print a[2]; exit }
    in_block && /adapter / { in_block=0 }               # new adapter section = stop looking
')
ETHERNET_IP=$(echo "$IPCONFIG" | awk '... same pattern for "adapter Ethernet:" ...')
LOCAL_IP="${WIFI_IP:-$ETHERNET_IP}"   # WiFi first, Ethernet fallback
```

Key bug that was found and fixed: without `next` after `in_block=1`, the same adapter header line that opens the block also matches the `/adapter /` reset pattern, immediately closing it. `next` skips all remaining rules for that line.

`\r` stripping is required because Windows `ipconfig` produces `\r\n` line endings which break awk pattern matching in Git Bash.

If neither adapter has an IPv4, the script aborts with a clear error before launching anything.

**`App/.env` (auto-generated, never commit):**
```
VITE_LOCAL_DEV=true
VITE_LOCAL_IP=<detected IP>
LOCAL_IP=<detected IP>
```

Vite reads this via `envDir: '../'` in `vite.config.js`. Flask reads it via `load_dotenv` in `backendLocalConfig.py`.

**`App/frontendLocalConfig.jsx`** now reads:
```js
export const url = local
    ? `http://${import.meta.env.VITE_LOCAL_IP}:5000`
    : "https://cashflow2-0.onrender.com";
```

**`App/backendLocalConfig.py`** now reads:
```python
LOCAL_IP = os.environ.get('LOCAL_IP', '')
CORS_ORIGINS = [f"http://{LOCAL_IP}:5173"] if LOCAL_DEV and LOCAL_IP else [...]
```

### Files changed

- `start-dev.sh` — IP detection + `.env` write before server launch
- `App/frontendLocalConfig.jsx` — reads `VITE_LOCAL_IP` from env
- `App/backendLocalConfig.py` — reads `LOCAL_IP` from env
