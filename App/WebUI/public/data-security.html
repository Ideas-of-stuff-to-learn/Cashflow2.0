Cashflow 2.0 — Security Overview

Your data security,
explained plainly

This document explains what protections are in place, what information the developer can technically access, and why that limitation is an unavoidable property of how cloud apps work — not a gap that was overlooked.

The journey your data takes

Every time you log in, upload a file, or view your transactions, your data moves between your browser and a server. Here is what happens at each step.

What is protected, and how

🔒

Passwords are never stored

Your password is run through bcrypt — a one-way mathematical process — before anything is saved. The result is a fixed-length string of scrambled characters that cannot be reversed back into your original password. Not by code, not by the developer, not by anyone.

🌐

All traffic is encrypted

Every connection between your browser and the server uses HTTPS with TLS. Your transaction data and login details are encrypted in transit — anyone intercepting the network traffic sees only scrambled noise.

🍪

Login tokens stay out of reach

After you log in, your session is tracked with a short-lived httpOnly cookie. This means the token is invisible to JavaScript — a malicious script on a compromised page cannot steal it. Tokens expire after 24 hours; a longer-lived refresh token expires after 30 days.

🛡️

Input is sanitised

Every database query uses parameterised placeholders — the standard method that makes SQL injection impossible. Transaction descriptions are also stripped of characters that could become spreadsheet formulas if the data were ever exported.

⏱️

Login attempts are rate-limited

The login endpoint accepts at most 10 requests per minute per IP address. A brute-force attack that tries thousands of passwords is blocked automatically.

🤖

AI categorisation is minimal

When automatic matching cannot categorise a transaction, only its description text is sent to Google's Gemini API. No amounts, dates, or account details leave the server in that call.

What the developer can see

This is the part most apps leave out of their security pages. It deserves a straight answer.

The app's data lives in a PostgreSQL database hosted on Supabase. As the developer, direct administrative access to that database is available. That means the following is technically possible.

Developer can see
  • ⚠️ Transaction descriptions, amounts, and dates you have uploaded
  • ⚠️ Your username
  • ⚠️ Which categories you have assigned
  • ⚠️ Names of files you have uploaded
Developer cannot see
  • ✅ Your password — stored only as an irreversible hash
  • ✅ Your active session token — short-lived, not persisted
  • ✅ Any data from other apps or services — only what you upload here
  • ✅ Your full account numbers — bank files typically only contain the last few digits
Honest note

This is the reality of any cloud-hosted application where the server processes your data. The developer of Gmail can query your emails. The developer of a cloud accounting tool can query your transactions. The distinction worth noting is that this app is a personal tool — there is no commercial incentive to look at your data, no advertising model, and no third parties it is shared with.

Why this limitation cannot be removed

The only technical way to prevent the server from ever reading your data is client-side encryption — encrypting everything in your browser before it is sent, so the server stores only ciphertext it cannot read.

The problem: the server then cannot do anything useful with it. Categorising transactions, running the matching pipeline, calling the Gemini API — all of these require the server to actually read the transaction descriptions. Encrypting the data before sending it would mean the server processes nonsense, and the app stops working.

This is a fundamental property of server-side computation, not a design choice. Any app that processes your data on a server — whether it is a banking app, a budgeting tool, or a payroll system — has this same property. The tradeoff is capability versus zero-knowledge: you cannot have both at the same time.

The practical reality

The meaningful protection here is not technical — it is contractual and legal. The Privacy Policy commits to not sharing or selling your data. Your transaction data is not interesting to misuse: it contains spending patterns, not credentials that could be used anywhere else. And the developer is personally identifiable and accountable — this is not an anonymous service.

Summary

  • 🔐 Passwords are protected by one-way hashing and cannot be recovered by anyone.
  • 🌐 All data in transit is encrypted end-to-end with HTTPS.
  • 🍪 Session cookies are httpOnly and short-lived — invisible to JavaScript.
  • 🛡️ The database uses parameterised queries throughout — SQL injection is not possible.
  • ⚠️ Transaction data stored in the database is readable by the developer as the database administrator — this is true of all cloud-hosted applications.
  • 🚫 This cannot be removed without also removing the ability to process your data server-side.
  • 🤝 No data is sold, shared with advertisers, or passed to third parties beyond the minimal Gemini API call for categorisation.
