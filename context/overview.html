Project Overview

Cashflow2.0

A personal-finance tracker that turns uploaded bank statements into auto-categorized spending charts, using a tiered matching pipeline (exact → merchant → fuzzy → AI) so the app needs less manual tagging over time.

Current Since the last major change

Most recent work, newest first.

The phone version of the app renamed internally for clarity

The folder holding the phone/tablet app's code used to just be called "UI," which was easy to confuse with the website's own UI code sitting right next to it. It's been renamed to make clear it's specifically the native phone app, and every startup script and configuration file that pointed at the old name has been updated to match.

The phone app's category filters caught up to the website's new combined design

Following on from the website change described below, the phone app's category-selection screen and its separate reordering screen have been merged into one the same way — each category now shows as a single row with a checkbox and a drag handle, instead of two separate lists to manage. Dragging works by press-and-hold on the handle and moving your finger up or down, which is the natural touchscreen equivalent of dragging with a mouse. The phone app's charts screen also had its own redundant summary chart removed, to match the website.

Combined the category filter list and the reorder list on the website into one

The website previously had two separate ways to control how spending categories appear on the charts: one list of checkboxes to turn categories on/off, and a completely separate list with up/down buttons to change their stacking order. Both listed the exact same categories, just for two different purposes. They're now one single list — each row has a checkbox, a colour swatch, the category name, and a drag handle, so ticking a category and reordering it happen in the same place instead of two.

Dashboard now fits on one screen without scrolling

The main dashboard page was reworked so that, at a normal screen size, everything — the header, the spending chart, the category filters, and the explanatory footnote text — fits within the visible area at once, with only the transaction list (a separate page) still expected to scroll. This took several rounds of tracking down exactly which part of the page was scrolling when it shouldn't, including one genuinely subtle browser quirk: a rule that says horizontal scrolling and vertical scrolling can't be set independently in one specific combination, which was silently creating an extra, unwanted scrollbar. Once identified, that was a one-line fix.

The filter panel can still be collapsed down to just its title bar to save space, and it no longer has the option to be dragged to the opposite side of the screen, which wasn't being used and only added visual clutter.

Chart pop-up behaviour is now a single setting instead of scattered logic

When you tap a bar on the spending chart, a small pop-up shows the details. Previously, exactly where that pop-up appears and how it's triggered was buried inside several different files. That's now controlled from one settings file per platform, so changing how the pop-up behaves in the future (or making it consistent between the website and the phone app) is a small, contained change rather than a hunt through the codebase.

Known rough edges

Things a future contributor should know are provisional.

Grouped by which part of the codebase they live in.

Backend

No automated tests exist anywhere in the Flask app — the categorization pipeline and permission logic are only ever checked by hand.
No database migration system — schema changes are applied by directly editing the schema file, with no history or rollback.
Working CSV files sit inside the backend source folder rather than in a fixtures or scratch directory — harmless, but easy to mistake for something the code actually depends on.

Admin CLI

Always points at the live production server — there's no setting to make the admin tools talk to a local/test backend instead, so every admin action is run against real data by default.
Inconsistent internal structure — some of its sub-folders are set up as proper importable modules and some aren't, with no functional difference today but worth tidying for consistency.
A colour palette is manually copy-pasted between the admin tool and the two apps rather than shared from one place, and the comment pointing at where the "real" copy lives is itself out of date.
Older internal notes reference a CLI location that no longer exists — the tools have only ever lived in one place; any mention otherwise is stale.

Web app

No automated tests, no type-checking — same caveat as the backend, and now covers larger pieces (chart windowing, manual review, the newly combined filter panel) with no test coverage at all.
A shared constant is duplicated in three places across the codebase instead of one canonical copy, so it's possible to update one copy and miss the others.
The top-level README files are placeholders — this document and the accompanying technical handoff notes are the real documentation.

Native mobile app

The chart pop-up settings file isn't actually wired up yet — the phone app has its own separate, hardcoded pop-up behaviour; the new shared settings file exists for consistency of naming but doesn't control it yet.
Drag-to-reorder is a hand-built touch gesture, not a polished animated one — it works, but the category row doesn't visually follow your finger while dragging the way it might with a dedicated animation library (which is already available if that polish is wanted later).
No automated tests, same as the other two parts of the system.

Major change Manual review optimisation & chart/mobile parity

What changed in this milestone, newest-first within it.

Fixed: reviewing leftover transactions one at a time was slow, and closing the tab too early could lose your progress

When a batch of uploaded transactions couldn't be automatically sorted into a category, the app asks the person to go through them one by one and pick a category. Previously, every single pick was sent to the server immediately, so reviewing fifty transactions meant fifty separate round trips to the server before you could move on. Now the app collects all your picks locally and sends them all at once in a single request when you finish, which makes the review flow feel instant. If the final save fails, the app keeps your picks and shows a retry button instead of making you start over.

Separately, the "just put everything left over into a generic category" option used to ask the server to update each leftover transaction one at a time behind the scenes. It now tells the server to update all of them in one single instruction, which is much faster for people with a lot of leftover transactions.

There was also a gap where, if someone closed the browser tab in the middle of reviewing transactions, any leftover unsorted ones could stay stuck in limbo. A safety check now runs automatically the moment the tab starts closing, sweeping any remaining unsorted transactions into the generic category so nothing gets lost or stuck.

Fixed: unchecking every spending category left the chart looking like nothing was filtered

The spending charts let you tick and untick categories to control which ones show up as bars. A leftover piece of logic from an earlier version of the filtering system meant that if you unticked every single category, the chart mistakenly treated that as "show everything" instead of "show nothing." This has been corrected so that unticking all categories now correctly empties the chart, matching how every other filter in the app behaves.

Mobile app brought up to match the web app's chart experience

The mobile (phone/tablet) version of the app previously had a simpler set of charts than the website. This round of work rebuilt the mobile charts so they behave the same way as the web charts — same scrolling and windowing behavior, the same tap-to-see-details popup on each bar, and the same filtering behavior — so switching between using the app on a computer and on a phone feels consistent.

Easier local setup for developers

Starting the project on a new computer used to require manually figuring out network addresses and hand-editing configuration files. A new startup script now detects the right local network address automatically and generates the needed configuration files itself, so a developer can start the whole system (website, mobile app, and server) with a single double-click instead of manual setup steps.

Major change Original build

The system as it stood before the most recent round of work.

The project was originally built as a mobile-only app, then later gained a full website version alongside it, so the same features now work on both a phone and a computer. Over a series of past working sessions, the project grew from a simple statement-upload tool into a fuller system: automatic categorization of transactions using multiple fallback strategies (including an AI step for anything unclear), spending charts broken down by month and year, a searchable and filterable transaction list, user accounts with different permission levels (owner, admin, regular user), and an automated nightly backup of the database. A step-by-step review screen was added for any transaction the automatic system couldn't confidently sort on its own.

This baseline reflects the state of the project heading into the most recent round of work described above — it is a summary of prior progress rather than a single dated event, since the detailed session-by-session history lives in the project's internal engineering notes rather than in this document.
